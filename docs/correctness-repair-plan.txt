Two delivery milestones are proposed:

M1: a restricted, tested file server with honest capabilities and no grants of unfinished optional behavior. Optional features can remain unavailable, but mandatory requirements for every offered dialect still apply. M1 is not closure of a finding whose only mitigation is disabling a feature.

3.2 Mandatory red-green-refactor development

Every correctness repair and new supported behavior must follow test-first red-green-refactor:

1. RED: write the smallest meaningful regression or acceptance test for the required behavior. Run it against the current unfixed maintained source and observe a failure for the intended reason before changing production behavior. Capture the command, baseline revision/diff state and relevant output. A compilation error, missing dependency, skipped test or unrelated fixture failure is not evidence of the behavioral defect.
2. GREEN: make the smallest coherent production change that satisfies the contract. Run the same test and record its passing result, then run the relevant existing regression tests. Do not weaken assertions, remove the test, or alter expected results solely to accommodate the implementation.
3. REFACTOR: improve structure only after green, keeping the new test and affected regressions passing. Preserve reviewable separation between reconstruction, repair and unrelated cleanup.

For races, RED must use controlled ordering/barriers where practical and a bounded timeout to detect a stuck operation; a theoretical race description alone is not completed TDD evidence. For wire contracts, expected results come from the specification or independent fixtures rather than the server code under test. A failing external conformance case may supply RED when its environment, expected result and repeatability are documented.

P0 compiler-artifact reconstruction and test-tool setup are prerequisites to behavioral TDD, not correctness repairs disguised as setup. Record baseline build failures and subsequent successful builds separately, and do not mix behavior changes into reconstruction. Once the relevant code is executable, add and observe the behavioral RED before its fix. If a finding cannot be made to fail as expected, investigate, narrow or reject it with evidence; keep it unconfirmed or blocked rather than claiming it fixed. Any exception to mandatory test-first behavioral work requires an explicit user-approved change to this plan.

P2. Establish stable file identity and transactional open lifecycle

Findings: F02 identity foundation, F08, F09, F16; complete F01 semantics.
Entry points: State/SmbConnection, SmbSession, SmbTreeConnect, SmbOpen; CREATE/CLOSE/TREE_DISCONNECT; LocalFileStore/LocalFileHandle; lock/share/oplock maps.

Tasks:
1. Allocate TreeIds and volatile FileIds in the namespace of their resolving tables, not per connection. Use checked allocation, reserved-value rules, collision-detecting insertion and an explicit wrap/exhaustion policy. Preserve tuple uniqueness for persistent/volatile file IDs. Never replace a live entry through dictionary index assignment.
2. Introduce stable backend object/stream identity for the lifetime of an open. Distinguish it from request pathname and protocol FileId. Key locks, share reservations, delete-pending and caching state by that identity. On local stores, choose a host-supported identity strategy or explicitly constrain unsupported aliases; a normalized string path alone does not solve rename or hard-link behavior.
3. Make CREATE a staged transaction: provisional share reservation -> backend acquisition -> response/context preparation -> open publication -> successful completion. Track every acquired resource with a rollback owner. On exception/failure, release reservations, handles, map entries, cache/recovery records and counts exactly once. Define send-failure cleanup separately from ordinary pre-commit failure. Do not promise rollback of backend side effects the backend cannot actually reverse.
4. Model Open transitions such as provisional, active, closing, closed and, later, durable-disconnected. Add operation references so close prevents new work and drains/cancels in-flight work according to its contract. A concurrent dictionary does not make multi-step lifecycle operations atomic.
5. Centralize protocol close and resource cleanup. TREE_DISCONNECT closes matching opens and cancels associated work before removing its tree. Reuse the routine for CLOSE, logoff, connection loss, timeout, shutdown and failed CREATE, with reason-specific retention rules. Do not apply durable retention to explicit close/tree disconnect just because a handle is durable.
6. Coordinate rename with the stable object registry and all open handles. Update names and path-derived metadata without losing lock/cache/share state. Define replacement behavior for destination opens and delete-pending objects.

Acceptance:
- Two channels attached to a shared session allocate distinct IDs; no existing table entry is overwritten. This unit test does not enable multichannel on the wire yet.
- Faults injected after each CREATE acquisition leave no provisional resources or unreturned active opens.
- TREE_DISCONNECT returns resource counters to baseline, including backend handles, reservations, locks and watchers.
- Rename while open preserves locks and metadata for all opens; subsequent unlock/close works.
- Concurrent close, I/O, rename and tree teardown have one cleanup owner and no use-after-dispose behavior.

P3. Repair compound execution, credit accounting and structural parsing

Findings: F04, F07; parser follow-ups in the review.
Entry points: Smb2Dispatcher.ProcessMessageAsync, Smb2Header, CreditManager, request parsers and response assembly.

Tasks:
1. Introduce a compound execution context containing the prior result's SessionId/TreeId/FileId, related-chain membership, failure/dependency state, current command bounds and pending continuation. Resolve related placeholders according to the command rules; do not inherit literal placeholders or values from the previous request when the response created new identifiers.
2. Keep unrelated commands independent and prevent identifiers from leaking between chains. Propagate prerequisite failure using the required status behavior. Preserve response flags, alignment and command-relative offsets. Ensure a dependent command cannot run before the preceding operation completes.
3. Connect asynchronous compounds to P4's completion machinery. Until that path is implemented, use only the specification-permitted unsupported behavior; never perform dependent mutation before completion of a parked CREATE.
4. Replace the moving sequence-window lower bound with an available/granted/consumed sequence ledger. Consume the correct range once per applicable request and extend it by actual response grants. Handle valid out-of-order sequence arrival, command-specific exceptions, compound elements, multi-credit sizes, overflow and asynchronous grants explicitly.
5. Calculate required charge from command-specific request/expected-response sizes and negotiated large-MTU/dialect rules. Related operations must not bypass required sequence/charge processing. Preserve valid CANCEL handling rather than treating it as ordinary request consumption.
6. Check fixed structure sizes, required fields, compound NextCommand alignment/range, CREATE name encoding/offset rules, and command-local lengths. Centralize structural checks without collapsing distinct command error semantics into one generic result.

Acceptance:
- CREATE -> READ/WRITE -> CLOSE and tree-generating related chains work with inherited identifiers.
- An unsuccessful prerequisite prevents dependent operations; unrelated requests continue under their own rules.
- Complete serialized responses have correct chaining and command-relative offsets.
- Ledger model tests cover out-of-order valid IDs, consumed IDs, grant changes and multi-credit operations around size boundaries.
- Parser boundary tests exercise valid and invalid structure/offset combinations without a network exposure requirement.
- A pending related operation resumes only through P4's explicit continuation.

P4. Repair cancellation, asynchronous completion and notifications

Findings: F05, F06, F14; CANCEL scheduling follow-up.
Entry points: InMemoryLockManager, PendingRequests, SmbConnectionHandler, lock/notify/parked-CREATE handlers, IDirectoryWatcher/FileSystemDirectoryWatcher.

Tasks:
1. Remove waiters under the lock-manager gate, but dispose cancellation registrations and complete tasks outside it. Define one winner for cancel versus grant. Avoid inline continuation execution while holding shared manager locks.
2. Introduce a pending-operation state machine with registered, interim committed, completing and completed states. Publish pending identity before enabling completion sources. If the operation takes the pending path, queue early completion until the interim response has been committed to the ordered sender. Permit synchronous completion without a redundant interim when the protocol allows it.
3. Centralize exactly-once completion, response ownership, cancellation and resource removal. Maintain both appropriate original MessageId lookup and AsyncId lookup. Define behavior when the transport closes before interim/final transmission.
4. Allow CANCEL and teardown to reach pending operations without waiting behind a blocked backend READ/WRITE. Preserve required ordering of actual file operations while separating control-plane progress. Document backend cancellation limits; do not claim physical I/O cancellation when only response delivery can be cancelled.
5. Maintain notification state per directory open, including active filter/subtree semantics, bounded queued changes, pending request ownership and watcher lifetime. Empty/all-invalid filters must follow the documented pending behavior, not a substituted default filter.
6. Handle FileSystemWatcher.Error/overflow with the specified rescan/completion semantics. Preserve changes across re-arm where required, and distinguish expected rescan behavior from silent loss. Bound buffers and release subscriptions on close, tree disconnect and shutdown.

Acceptance:
- Deterministic barrier tests cover cancel before/after registration, cancel versus grant, disconnect during completion and close versus notify.
- No registration disposal waits while holding the callback's required gate.
- Every pending-path final response follows its interim response; every operation completes once or is explicitly abandoned on transport loss.
- Pending maps, subscriptions, callbacks and locks return to baseline after each scenario.
- Notification tests cover empty filters, subtree changes, rename pairs, overflow, changes between calls and cancellation.
- Controlled short stress tests supplement deterministic tests; timing-only tests are not the sole evidence.

P5. Make file commands honor their contracts

Findings: F10, F11, F12, F13; COPYCHUNK and metadata follow-ups.
Entry points: WriteMessage, ReadMessage, QUERY_INFO/IOCTL/SET_INFO/QUERY_DIRECTORY handlers, IFileStore, LocalFileStore and pipe buffering.

Tasks:
1. Parse WRITE flags/channel fields completely. Carry supported write-through/buffering intentions through the backend API and validate unsupported channel combinations. Distinguish MUST requirements from SHOULD behavior; document a permitted host limitation rather than inventing durability guarantees. Keep explicit FLUSH coverage.
2. Enforce READ Length and MinimumCount with the correct zero-length/EOF behavior. For QUERY_INFO and IOCTL, implement per-class short-buffer and partial-output rules. For pipes, preserve unread output with a cursor/message-aware buffer rather than draining all queued bytes. Do not apply generic truncation to every response.
3. Parse and validate FileAllocationInformation. Add an allocation capability and implement supported allocation/EOF effects, rounding and failure semantics; otherwise return the required unsupported result. Do not equate allocation size blindly with logical EOF or report success for a no-op. Backend guarantees may differ by host.
4. Model directory enumeration state explicitly. Honor REOPEN and RESTART_SCANS, pattern changes, RETURN_SINGLE_ENTRY, buffer-limited pagination and EOF. Ensure a bounded backend listing can resume rather than permanently losing entries beyond its first batch.
5. Route COPYCHUNK through the same source/destination range-lock, lifecycle and cache-coherency coordination as equivalent reads/writes, accounting for overlapping ranges and partial failure according to the FSCTL contract. Keep it unavailable until that integration passes.
6. Define the supported local-store metadata contract: named-stream/EA persistence, restart behavior, rename consistency, timestamps and case-sensitive host behavior. Unsupported persistence guarantees must not be represented as full NTFS semantics. Security-oriented path isolation stays excluded.

Acceptance:
- Exact-size, short, zero and boundary-sized response tests cover each supported information class and pipe operation.
- Writes invoke the intended backend durability behavior; actual power-loss durability is not inferred from a mock flush counter.
- Allocation requests change state correctly or return an honest unsupported result, including disk-full/error cases.
- Enumeration survives restart/reopen, changed patterns and multiple output-buffer pages.
- COPYCHUNK respects both source and destination locks and has tested partial-result behavior.
- Metadata features have a documented persistence contract and matching restart/rename tests.

P6. Implement coherent oplocks and leases before restoring grants

Finding: F03, with F09/F16 lifecycle integration.
Dependencies: stable file identity, transactional lifecycle, pending-operation state machine and operation-specific coordination.

Tasks:
1. Use a common per-object/stream conflict coordinator for lease and oplock state. Represent granted state, requested downgrade, break epoch/acknowledgment and timeout explicitly.
2. Decide conflicting-operation requirements before backend truncation, overwrite, write, rename, delete, size changes and copy operations. Park operations requiring a break until the protocol permits proceeding. Do not hold global locks while awaiting acknowledgments or backend I/O.
3. Apply the same rules to ordinary and compounded commands, aliases, multiple opens and reconnects. Define host-side modification handling; if a backend cannot coordinate external changes, withhold caching rights for that backend or restrict its supported access model.
4. Handle acknowledgment, timeout, client disconnect, cancellation and duplicate completion through P4's lifecycle. Avoid separate managers making incompatible grants for the same underlying file.

Acceptance:
- Two independent clients observe consistent contents through conflicting read/write/overwrite/rename workflows.
- A destructive operation cannot modify the backend before its required break acknowledgment/timeout decision.
- Mixed lease/oplock opens, related CREATE chains and disconnect during a break have deterministic outcomes.
- Grant flags and negotiation claims match implemented behavior. Restore only individually validated cache rights; unsupported directory leases remain explicitly unavailable.

P7. Implement multichannel sequencing and recovery in separate stages

Findings: F02 final closure and F15.
Dependencies: P2 identity/lifecycle, P3 credits, P4 async ordering, P6 caching where recovery preserves it.

Tasks:
1. Implement mandatory SMB3 channel-sequence processing for the offered dialects, with per-open current/prior sequence state and outstanding-request accounting. Validate old/new sequence handling and mutation ordering. Disabling multichannel does not waive dialect-mandated checks.
2. Serialize compound/lifecycle transitions across channels where necessary while allowing independent I/O. Preserve per-connection credit accounting and shared-session open identity. Handle loss of one channel separately from loss of the entire session/connection set.
3. Implement CREATE replay deduplication and each supported operation's replay/lock-sequence behavior. Scope replay records, results, retention and retirement to the protocol rules. Do not implement a generic replay cache without command semantics.
4. First validate basic in-memory durable reconnect: retained handle, locks/share state, timeout, explicit close, disconnect and reconnect. Keep this distinct from restarting the server process.
5. Treat persistent handles/CA as a separate backend capability and journal design. Record enough stable object identity, lock/cache/delete-pending/replay state to recover the promised semantics. Define atomic commit, versioning, crash points and stale-record cleanup. Reopening a pathname with saved IDs is insufficient.
6. If the backend cannot provide persistent/CA semantics, leave them unavailable and mark that limitation explicitly. Full persistent/CA completion then remains deferred, not falsely closed. Authorization checks on binding/reconnect remain outside this work.

Acceptance:
- Multiple connections create/open/close without ID collisions or leaked entries.
- Controlled cross-channel ordering and lost-response scenarios do not duplicate supported mutations or lose established lock state.
- Durable tests cover success, expiration, explicit close and transport interruption.
- Persistent/CA claims require process-restart/crash-recovery tests with the promised state preserved; otherwise no such claim or grant is emitted.
- Enabling any feature requires its own passing gate, not simply setting EnableMultichannel=true.

6. Run bounded concurrency and ordinary backend-failure tests; track open counts, pending requests, watchers, lock waiters, reservations, recovery records, file descriptors and memory trends. Require quiescent resources to return to expected baseline, allowing explicitly retained durable state only within its timeout.
7. Verify reproducible clean restore/build/test/publish steps and dependency license records. Pin dependencies and remove accidental references to original package assemblies. Keep issue evidence and final feature limitations with release artifacts.

Recommended optional Microsoft suite integration:
- Prefer establishing a baseline soon after P0 produces an executable maintained server, rather than waiting until the final milestone. Pin a suite revision and begin with a small explicitly selected set of ordinary file-operation tests against disposable shares in a workgroup setup.
- The suite is MIT licensed and runs as a separate network test client. It adds no protocol implementation dependency to the shipped C# library; its runner need not be Native AOT. Configure the selected tests against both JIT and Native AOT server hosts when practical.
- Map relevant cases to findings for compounds, credits, file lifecycle, read/write, enumeration, locks, cancellation, notifications and cleanup after inspecting actual case coverage. Add advanced-feature cases only as those features are implemented and advertised.
- Use applicable cases to supplement mandatory red-green-refactor: capture an intended failure before the fix, then rerun after the fix. Retain focused local regression tests, especially deterministic scheduling and resource-lifetime tests; external suite setup failures or skipped cases do not count as behavioral RED evidence.
- Budget for configuration, server/share reset and any custom server-control adapters. Keep authorization, authentication/signing and encryption verification excluded under the existing scope; ordinary session setup may still be needed to run file-operation tests.
- If setup cost or environmental limitations prevent integration, record the deferral and continue using the required local regression, interoperability and AOT checks. Missing Microsoft suite integration alone must not block P0, P8, M1 or M2. Confirmed correctness failures discovered by optional tests still require a disposition; optional integration is not permission to ignore defects in claimed functionality.
- Passing selected tests is evidence for those scenarios, not full protocol coverage or certification. Record the exact selection and exclusions with the results.

Do not relabel mitigation as implementation. Optional unsupported behavior is not automatically a defect, but mandatory dialect behavior cannot be waived by configuration notes.

5. Validation discipline and stop conditions

Mandatory red-green-refactor and the required delegation hierarchy in sections 3.1 and 3.2 govern every implementation phase. No correctness batch is accepted without an observed, relevant RED followed by GREEN and passing affected regressions. For concurrency, force interleavings with barriers instead of relying solely on sleeps. Tests should assert external results and resource invariants rather than copy the implementation. For source ambiguity, original IL inspection is preferable to guessing from lowered async/goto syntax.

Keep reconstruction and correctness patches reviewable independently. Never compare correctness only with the original DLL: it may contain the same defect. Use the Microsoft requirements and independent client behavior as checks, documenting permitted implementation choices and SHOULD deviations.

Stop feature restoration if a prerequisite invariant fails. Keep the restricted profile available while repairing an advanced feature. If source reconstruction reveals extensive unresolvable decompiler artifacts, assess replacing only the affected subsystem behind preserved interfaces rather than accumulating unreviewable edits. If an excluded authentication/encryption path prevents integration testing, record the blocked coverage and keep the feature unvalidated; no exemption from that failure is assumed.

Implementation estimates should be made after P0 exposes buildability and P2 settles backend identity/API changes. The highest-uncertainty work is cross-platform stable identity, cache coherency, cross-channel ordering and persistent recovery. This is a multi-stage correctness project, not a fixed small patch count.

6. Completion criteria

M1 completion requires P0 through P5, applicable mandatory dialect handling from P7, and the P8 gate for the restricted feature set. It includes a clean source/AOT host, passing basic file and concurrency contracts, coherent advertised limitations, and a disposition for every finding. The coordinator must verify the recorded RED/GREEN evidence for every accepted correctness batch. Optional-feature findings may still be mitigated or deferred and must remain visible.

M2 completion requires the selected advanced features from P6/P7 to pass their own P8 gates. If full persistent/CA recovery is not implemented, M2 must explicitly exclude it rather than representing all 16 findings as fully implemented. The final result includes maintained source, regression tests, reproducible build instructions, capability records, dependency/license records, and the final finding ledger.

Security scope remains excluded from both milestones. Completion establishes only the tested correctness surface, not general production readiness or a security certification.
