SMB-Server 2.1.1 — independent static protocol/reliability review
Review date: 2026-11-07

SCOPE AND EVIDENCE

Reviewed the ILSpy-generated C# under /mnt/storage/SMB-Server/decompiled, concentrating on reachable Smb.Host -> Smb2Dispatcher -> LocalFileStore behavior and the default state managers. Original package binaries were not changed. This report is a defensive, non-security review of protocol conformance, incompleteness, data correctness, concurrency, and cleanup.

Per the user's revised scope, authorization, authentication, signature verification, encryption, key derivation, preauthentication integrity, and security-oriented path-isolation analysis are excluded. No conclusion about security in those areas should be inferred from their omission. Earlier observations in those areas are deliberately not included here.

Runtime validation did not complete. No reproduction harness or attack payload was created or run for this review. Every finding below is based on static source inspection and, where stated, primary Microsoft specification/API documentation. No finding is described as runtime-reproduced. Original IL was not independently inspected; the decompiled projects were not rebuilt. Straightforward calls, field assignments, missing state propagation, and missing checks are strong static evidence; concurrency timing and resulting client behavior remain unmeasured.

Decompiler-generated type names, redundant constant expressions, goto labels, lowered async constructs, and enum subtraction expressions are not themselves findings. The findings do not depend on compilation failure of the decompiled source. Particular caution was applied to unusual enum tests: the cache-coherency finding below rests on operation ordering and missing integration rather than interpreting one suspicious decompiled enum expression.

ASSESSMENT

This is substantially implemented software, not an empty protocol skeleton. It contains real framing, parsers, file operations, a concurrent I/O pipeline, range locks, notification adapters, and durable-handle machinery. Nevertheless, the inspected code has serious correctness defects in common paths. Ordinary operations can delete more data than requested, address the wrong open after multichannel allocation collisions, fail valid related compounds, leave files open after a tree disconnect, or violate client caching assumptions. Successful status is sometimes returned for work that has not been performed.

Repair is technically plausible, but making this a dependable general-purpose SMB2/3 server is a substantial engineering and interoperability effort, not a small patch series. A narrowly scoped server with a reduced feature set is more plausible: disable grants for incomplete optional caching/recovery features, repair the basic state model and file semantics, then establish automated protocol and cross-client testing before expanding advertised capabilities. The author's reported migration to Samba was treated only as context, not as evidence for any finding.

Severity below measures reliability/data-integrity impact, not exploitability. High confidence means the source establishes the behavior; medium confidence means a concrete concurrency ordering or environmental condition still needs runtime confirmation.

PRIORITIZED FINDINGS

F01 — HIGH / HIGH confidence: deleting a directory on close recursively deletes its children

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.FileSystem/Smb/FileSystem/Local/LocalFileStore.cs:491-503
  /mnt/storage/SMB-Server/decompiled/Smb.FileSystem/Smb/FileSystem/Local/LocalFileHandle.cs:173-193
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:2480-2486

Condition: a writable LocalFileStore directory is marked delete-on-close through CREATE or SET_INFO and the handle is closed while the directory contains entries.
Actual: SetDeleteOnClose accepts the flag without checking whether the directory is empty. Dispose calls Directory.Delete(FullPath, recursive: true). Exceptions from deletion are swallowed.
Expected: deletion of a nonempty directory must not implicitly become recursive deletion; FileDispositionInformation documents STATUS_DIRECTORY_NOT_EMPTY. Ordinary SMB deletion of a directory is not a recursive-delete request.
Impact: unintended removal of an entire subtree; alternatively, failed deletion silently looks like a successful close. This is a concrete data-loss defect in the backend, independent of authorization.
Fix: use nonrecursive directory deletion, validate directory disposition using filesystem semantics, maintain delete-pending state at file/object level, and expose deletion failure through the appropriate operation rather than suppressing it.
Reference: [S01]. Evidence: static, not reproduced.

F02 — HIGH / HIGH confidence: multichannel can allocate duplicate TreeIds and FileIds inside one session

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/State/SmbConnection.cs:14-18,90-98
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:1008-1014,1142-1151,1498-1507,1554
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/State/SmbSession.cs:49-51

Condition: a session uses more than one bound connection, and creates trees or ordinary nondurable opens through different channels.
Actual: counters are connection-local and begin at zero, while successful channel binding attaches the same SmbSession object to each connection. TreeConnects and Opens are session-wide dictionaries. Ordinary opens all use PersistentFileId=0. Dictionary assignment can replace an existing entry when a second channel allocates the same counter value.
Expected: identifiers must be unique in the table in which they are resolved. MS-SMB2 explicitly requires FileId to identify an Open uniquely within Session.OpenTable.
Impact: an existing handle can subsequently address a different file; previous handles and their bookkeeping can become unreachable. Tree-table replacement can change the store selected for a request. This can occur during normal multichannel use; EnableMultichannel defaults to true.
Fix: allocate IDs in the session/global namespace, use collision-detecting insertion, and test simultaneous opens/tree connects across channels. Until fixed, disable multichannel advertisement and binding.
References: [S02], [S03]. Evidence: static, not reproduced.

F03 — HIGH / HIGH confidence: granted oplocks/leases are not integrated with all conflicting file operations

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:1515-1524,1561-1582,1616-1624,2257-2317
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Oplocks/InMemoryOplockManager.cs:26-52
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Leases/InMemoryLeaseManager.cs:34-89
  /mnt/storage/SMB-Server/decompiled/Smb.FileSystem/Smb/FileSystem/Local/LocalFileStore.cs:169-186

Condition: multiple clients/open handles access the same file while one holds a granted caching right; especially a conflicting overwrite/create or a write through another open.
Actual: the backend CreateAsync, including truncating dispositions, runs before lease/oplock break handling. Lease and oplock managers are separate branches rather than one file-wide coherency decision. The write path does not initiate cache breaks. A compounded CREATE does not take the standalone wait path even when break acknowledgments are outstanding.
Expected: once caching rights are granted, incompatible operations must coordinate with revocation/acknowledgment before performing conflicting work. Declining an oplock/lease is valid optional-feature behavior; granting it and failing to preserve coherency is not.
Impact: stale reads and lost/overwritten client-cached data. Presence of break-notification classes does not make the operation-level coherency implementation complete.
Fix: place cache-right conflict decisions before destructive/open operations, unify lease/oplock tracking per file identity, and apply coherency rules to WRITE, SET_INFO, COPYCHUNK, rename, and relevant external changes. Grant no caching rights until this is reliable.
References: [S02], [S04], [S05]. Evidence: static, not reproduced.

F04 — HIGH / HIGH confidence: related compounded requests do not propagate generated identifiers or failure state

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:448-451,477-500,1418-1421,1616-1624
  /mnt/storage/SMB-Server/decompiled/Smb.Protocol/Smb/Protocol/Messages/Smb2Header.cs:137-158

Condition: a normal related compound such as CREATE followed by a file operation using the previous result; a tree-generating operation followed by a dependent request; or an asynchronous operation followed by dependent commands.
Actual: the loop remembers only SessionId and TreeId from the preceding unrelated request, not values generated by its response. It never carries a FileId. Later file handlers parse literal IDs from their own body. There is no chain failure/dependency state. CreateResponse does not preserve RelatedOperations, and AssembleResponse does not add that flag. A break-dependent CREATE in a compound proceeds without the standalone pending/wait path.
Expected: inherit SessionId, TreeId, and FileId from the prior operation/result, propagate dependency failures, and retain the related-chain indication on responses. Dependent work must wait when a prior operation becomes asynchronous, or unsupported asynchronous compounds must be failed in the allowed manner.
Impact: common open/read/close compounds fail with FILE_CLOSED, later commands can run after a prerequisite failed, and response chains do not identify themselves correctly. This is core SMB2 behavior, not an optional optimization that can be silently ignored.
Fix: implement an explicit compound execution context with prior result identifiers, dependency/error state, and async continuation. Keep each command's offsets relative to its own sliced SMB2 header.
References: [S05], [S06]. Evidence: static, not reproduced.

F05 — HIGH / MEDIUM confidence: cancellation and lock wakeup can deadlock the global lock manager

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Locking/InMemoryLockManager.cs:78-88,117-142,175-186

Condition: cancellation is executing concurrently with release/unlock of a pending range-lock waiter.
Actual: the cancellation callback acquires _gate. ReleaseOwner and WakeWaiters call CancellationTokenRegistration.Dispose while holding _gate. Dispose waits for an already executing callback to finish. If that callback is waiting for _gate, both paths wait on each other.
Expected: callback unregistration/waiting must not occur while holding a lock needed by that callback.
Impact: operations using this shared lock manager can stop making progress, including unrelated files. The source establishes the lock inversion; occurrence/frequency was not measured.
Fix: remove waiters under _gate, then dispose registrations and complete tasks after releasing it; carefully handle cancellation/grant races using a single completion state.
Reference: [S07] (.NET API contract; this is an implementation deadlock, not a special SMB requirement). Evidence: static concurrency analysis only.

F06 — HIGH / MEDIUM confidence: async final responses can precede interim responses; notifications can leave stale pending entries

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:3316-3318,3439-3470
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Notification/FileSystemDirectoryWatcher.cs:45-46
  /mnt/storage/SMB-Server/decompiled/Smb.Host/Smb/Host/SmbConnectionHandler.cs:166-170

Condition: a range lock becomes available or a directory event arrives immediately around pending-request registration.
Actual: SendFinalLockResponseAsync is started before the interim response is returned to the host for sending. The directory watcher is activated before PendingRequests insertion; its callback can remove a nonexistent entry and send a final response, after which the handler inserts the already completed request and returns STATUS_PENDING. Serialized writes do not enforce logical interim-before-final order.
Expected: publish pending state and commit the interim response before an async completion can be sent; exactly one final completion must clean up exactly the registered request.
Impact: reversed response ordering, leaked pending-request slots, confused cancellation, and eventual resource-limit failures under notification activity.
Fix: add a registration/interim-sent barrier and a completion state machine; queue early results until interim transmission is committed. Apply the same design to lock, notify, parked create, and witness paths.
Reference: [S08]. Evidence: static race analysis only.

F07 — MEDIUM / HIGH confidence: credit accounting is a moving interval rather than the granted/consumed sequence ledger

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:612-639,799-800,2687-2692
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/CreditManager.cs:10-40

Condition: pipelining, related compounds, a client with multiple available sequence numbers, or multi-credit I/O.
Actual: receipt moves SequenceWindowStart to MessageId+charge, discarding lower unconsumed numbers. Window size is fixed at negotiation and does not grow/shrink with actual response grants. Related requests skip sequence validation entirely. ComputeCreditCharge is defined but has no server-side caller; handlers do not compare data/response size with the submitted charge. Grants generally return at least 256, independent of this window model.
Expected: maintain the available sequence set/ranges, consume each request's IDs once, extend the ledger by the credits actually granted, permit valid out-of-order arrival, and validate multi-credit payload charges.
Impact: valid traffic can be rejected, protocol flow control disagrees with what the client has been told, and advertised large-MTU behavior does not enforce its accounting contract. A generous credit policy is not inherently the bug; the inconsistent ledger is.
Fix: centralize credit consumption/granting and use an interval-set or equivalent ledger, including related operations and asynchronous credit handling. Validate payload charge before dispatch.
References: [S09], [S10], [S11], [S12]. Evidence: static, not reproduced.

F08 — MEDIUM / HIGH confidence: TREE_DISCONNECT removes the tree but leaves its opens and pending work alive

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:1183-1200,2157-2206

Condition: disconnecting a share while files or directory notifications remain open.
Actual: HandleTreeDisconnect removes only the TreeConnects entry and returns success. It does not close that tree's opens, dispose their backend handles, release sharing/locks/caching state, or cancel associated notifications. It also returns success when the tree did not exist.
Expected: close each matching Open before removing the tree and report an invalid/deleted tree appropriately.
Impact: persistent sharing violations, delayed deletion, live notification resources, leaked handles, and inconsistent later file operations until session teardown.
Fix: implement one reusable close-open routine and invoke it for each open on tree disconnect, close, logoff, timeout, and failure cleanup, with correct durable distinctions.
Reference: [S13]. Evidence: static, not reproduced.

F09 — MEDIUM / HIGH confidence: rename changes path-based lock identity without migrating lock/share/cache state

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.FileSystem/Smb/FileSystem/Local/LocalFileStore.cs:412-421
  /mnt/storage/SMB-Server/decompiled/Smb.FileSystem/Smb/FileSystem/Local/LocalFileHandle.cs:117-121
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Locking/InMemoryLockManager.cs:234-237
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Oplocks/InMemoryOplockManager.cs:101-104
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:2484,2499-2503,2811-2813

Condition: a file with active lock/cache/share state is renamed; or the same local file is opened through aliases that resolve to the same object.
Actual: Relocate changes the handle's PhysicalPath. Lock/oplock managers recompute dictionary keys from that path on later operations, while entries remain stored under the old key. Share-mode keys are based on share name and a lightly normalized request name and are not changed on rename. Other handles to the file retain their old FullPath.
Expected: renaming a file must preserve its open identity and associated locks, sharing restrictions, and cache state.
Impact: existing locks can become ineffective or unreleasable; reopening the old/new path can produce false conflicts or miss real ones. Metadata on another open can refer to a stale pathname.
Fix: key all managers by stable backend file/stream identity, not request path; maintain name mappings separately. Coordinate rename across open objects and metadata.
References: [S02] (Open/underlying-object semantics), [S04]. Evidence: static, not reproduced; filesystem-dependent alias behavior remains unmeasured.

F10 — MEDIUM / HIGH confidence: WRITE parsing drops write flags and channel information

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Protocol/Smb/Protocol/Messages/WriteMessage.cs:8,14-38
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:2257-2317
  /mnt/storage/SMB-Server/decompiled/Smb.FileSystem/Smb/FileSystem/Local/LocalFileStore.cs:186,287-306
  /mnt/storage/SMB-Server/decompiled/Smb.FileSystem/Smb/FileSystem/Local/LocalFileHandle.cs:101-110

Condition: WRITE carries write-through/unbuffered semantics or a channel value requiring validation.
Actual: the request record contains only offset, file IDs, and data; parsing stops before the channel and Flags fields. The backend write therefore cannot honor or reject those semantics. The LocalFileStore is opened without write-through options. Explicit FLUSH does flush to disk, but WRITE does not use it.
Expected: parse the complete fixed request, validate unsupported transport/channel combinations, and apply the requested durability/buffering semantics where required or recommended by the negotiated dialect. The specification's write-through propagation is a SHOULD, not an unconditional MUST; channel validation includes MUST requirements.
Impact: a successful write may carry weaker persistence semantics than the client requested, and unsupported request variants can be processed as ordinary writes.
Fix: carry flags/options through the request and backend APIs, validate them centrally, and implement supported durability semantics deliberately.
Reference: [S14]. Evidence: static, not reproduced.

F11 — MEDIUM / HIGH confidence: READ/QUERY_INFO and named-pipe replies do not consistently honor client size contracts

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Protocol/Smb/Protocol/Messages/ReadMessage.cs:8,29-30
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:2223-2227,2237-2254,2417-2428,1780-1788

Condition: a short read returns fewer bytes than a nonzero MinimumCount; QUERY_INFO supplies a small output buffer; a named-pipe response exceeds the READ length or IOCTL output allowance.
Actual: MinimumCount is parsed but ignored; only a zero-byte nonzero-length file read becomes EOF. Ordinary file/filesystem QUERY_INFO builds and returns the full structure without using OutputBufferLength. Pipe READ drains all queued output, and pipe IOCTL returns the full result without applying the caller's limit.
Expected: enforce MinimumCount, use the specified short-buffer status/partial-data rules for each information class, and bound pipe output while retaining unread data.
Impact: callers receive success where they should receive EOF or a size error, or receive more data than their protocol request allowed. Enumeration and RPC clients can mishandle these responses.
Fix: centralize bounded response construction and preserve pipe output cursors; add checks for each command's distinct status semantics rather than truncating everything indiscriminately.
References: [S15], [S16]. Evidence: static, not reproduced. Windows commonly uses MinimumCount=0, so that subcase will not affect every client.

F12 — MEDIUM / HIGH confidence: FileAllocationInformation is acknowledged without performing any allocation operation

Location:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:2480-2488

Condition: SET_INFO requests FileAllocationInformation.
Actual: the switch returns NtStatus.Success without reading the allocation value, validating the structure, or calling a backend operation.
Expected: perform the allocation-size operation and its validations, or report that it is unsupported. A successful status is not an honest representation of an unimplemented operation.
Impact: applications cannot rely on preallocation/truncation-related allocation semantics or expected disk-space errors.
Fix: add an explicit backend allocation capability and implement it; otherwise return the appropriate unsupported/error status. FilePositionInformation is also a no-op, but is not counted as a separate confirmed defect here because SMB's position semantics have explicit special cases.
Reference: [S17]. Evidence: static, not reproduced.

F13 — MEDIUM / HIGH confidence: QUERY_DIRECTORY ignores SMB2_REOPEN and reuses stale cached enumeration state

Location:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:2338-2373

Condition: a client reuses a directory open with SMB2_REOPEN to restart or change the search pattern.
Actual: only flags bit 1 (RESTART_SCANS) clears DirectoryListing/DirectoryCursor; REOPEN is not handled. Once cached, the prior listing is reused and the new pattern is ignored. RETURN_SINGLE_ENTRY is implemented.
Expected: both RESTART_SCANS and REOPEN restart the scan with the specified pattern. Support for index-based resumption is optional and its absence is not counted as a defect.
Impact: missing/wrong results, stale listings, or NO_MORE_FILES after a requested restart.
Fix: reset/reopen enumeration on both required flags; track the active pattern and enumeration lifecycle explicitly.
Reference: [S18]. Evidence: static, not reproduced.

F14 — MEDIUM / HIGH confidence: notification filtering and subscription lifetime are incomplete

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Notification/FileSystemDirectoryWatcher.cs:26-46,94-98
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:3435-3471

Condition: CHANGE_NOTIFY has no valid filter bits, the underlying watcher overflows, or changes occur between successive client notify calls.
Actual: an empty mapped filter is replaced by FileName|DirectoryName|LastWrite, rather than remaining pending. There is no FileSystemWatcher.Error handler. Each notification uses a new watcher and disposes it after the first completion; no per-open queued-change state bridges requests.
Expected: an all-invalid/empty filter remains pending until cancellation/close; watcher errors/lost-event conditions need an explicit result, and notification state should follow MS-SMB2's per-open change-notification algorithm.
Impact: spurious notifications for an empty filter; missed changes or indefinitely pending requests after watcher errors; possible gaps between subscriptions. The first issue is a definite conformance defect. Overflow/gap impact is a static reliability concern requiring workload validation.
Fix: maintain watcher/buffer state per directory open, implement error/overflow completion and explicit cancellation, and do not substitute an unrelated default filter.
Reference: [S19]. Evidence: static; timing/overflow not reproduced.

F15 — HIGH / HIGH confidence in missing processing: SMB3 channel sequencing/replay behavior is not implemented despite multichannel and durable machinery

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Protocol/Smb/Protocol/Messages/Smb2Header.cs:54
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:511-549,1423-1457,2935-3055
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/State/SmbOpen.cs
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Durable/PersistentHandleRecord.cs:5

Condition: SMB3 recovery/channel change, replay of operations after an uncertain response, or persistent-handle recovery after restart.
Actual: the header exposes ChannelSequence, but the server sources contain no use of it or ReplayOperation. There is no corresponding per-open channel-sequence/outstanding-pre-request state. CREATE does not deduplicate replay by CreateGuid. The persistent record contains path, IDs, owner key, create GUID and access/share masks, but does not preserve byte-range locks, lease state, delete-pending state, or the broader replay state; cold rehydration simply opens the path again.
Expected: the SMB3 channel-sequence checks apply to file operations, and replay-capable/persistent operation handling must preserve the relevant recovery semantics. Basic in-memory durable handles are not equivalent to full persistent/continuous-availability recovery.
Impact: delayed writes or replayed mutating operations may be executed with the wrong ordering or more than once; restored opens can lose previously established state. Exact real-client recovery effects were not exercised.
Fix: disable advertised/accepted recovery features until the required state machine exists; implement channel sequencing and idempotent replay, then persist/restore the object state needed by the supported recovery contract.
References: [S02], [S20]. Evidence: source search plus path inspection; no recovery runtime test.

F16 — MEDIUM / HIGH confidence: exception paths in CREATE do not consistently unwind acquired resources

Locations:
  /mnt/storage/SMB-Server/decompiled/Smb.Server/Smb/Server/Smb2Dispatcher.cs:1510-1527,1554-1566,1588-1606,1625-1642,553-561

Condition: a backend throws after share-mode reservation, or a later context parser/metadata operation throws after the backend handle/open was acquired.
Actual: normal failure return paths release some resources, but the overall CREATE body has no transactional finally/rollback. The outer dispatcher catches exceptions and returns an error. A reservation can remain after CreateAsync throws; a handle can remain untracked if a later pre-insertion operation throws; after insertion, an error can leave an open the client never received.
Expected: a failed CREATE must unwind its provisional resources and either commit a fully valid open/response or leave no open behind.
Impact: phantom sharing conflicts, leaked handles, incorrect open counts and eventual resource exhaustion during ordinary backend faults. This is not a claim that every backend throws in those locations; IFileStore implementations and filesystem faults make the path possible.
Fix: make CREATE a staged transaction with explicit rollback for reservations, handles, open-table insertion, cache state, and persistent records; commit only after all response-relevant work succeeds.
Reference: [S02] (failed/successful open lifecycle). Evidence: static, not reproduced.

ADDITIONAL COVERAGE AND LIMITATIONS

Framing/parsers: the host imposes the NBSS 24-bit frame-length ceiling; Smb2Header checks minimum length, protocol ID and structure size. Compound segments are sliced before body parsing, and response assembly aligns nonfinal segments. These are useful existing safeguards. Some validation is still incomplete: CreateRequest.Parse at lines 52-62 checks only the upper name bound, not the required even UTF-16 length or minimum NameOffset; READ/WRITE parsing does not consume/validate the full fixed request. ProcessMessageAsync checks NextCommand range but not alignment. These are follow-up conformance issues under [S02]/[S06], not claims of unmanaged memory corruption. F04 is the more consequential compound defect.

IOCTL: the dispatch switch has real implementations for selected FSCTLs and returns InvalidDeviceRequest for others. Unsupported optional FSCTLs alone are not bugs. COPYCHUNK at Smb2Dispatcher.cs:1826-1875 calls CopyRangeAsync directly, while the only IsRangeAccessible call sites in the server are ordinary READ and WRITE. Because LocalFileStore uses normal file handles and not this manager's byte-range state, the copy path does not honor the same in-memory lock checks. It also falls under F03's cache-coherency integration concern. This should be repaired before advertising broad server-side-copy interoperability; no copy/lock runtime check was completed.

Sharing/locks: both-direction share-mode conflict logic and multi-element lock bookkeeping exist. They are not empty stubs. File identity, rename consistency, cancellation disposal, and recovery integration are the important defects described above. Lock sequence/replay behavior is also incomplete; no claim of comprehensive LOCK conformance is made.

Cleanup/concurrency: per-connection concurrent READ/WRITE limits and serialized transport writes exist. The barrier in SmbConnectionHandler.cs:166 drains ordinary I/O before handling commands such as CANCEL, so cancellation cannot promptly reach a blocked backend READ/WRITE; those operations are not represented in PendingRequests anyway. This is an important cancellation limitation rather than proof that every I/O is required to be cancellable. Cross-channel operations have separate dispatcher scheduling queues, and concurrent dictionaries alone do not make the multi-step open/close lifecycle atomic. Broader cross-channel race testing remains necessary.

Filesystem metadata: explicit FLUSH reaches Flush(flushToDisk: true), so this operation is implemented. The backend's alternate streams and EAs are held in dictionaries, and file metadata is often path-derived. Their persistence and rename behavior should be documented and tested separately; this review does not certify full Windows filesystem semantics. Case-sensitive host filesystem behavior and symbolic-link policy were not reviewed for security or isolation under the revised scope.

Negotiation/capabilities: dialect selection covers 2.0.2 through 3.1.1; default options enable multichannel and install real in-memory oplock/lease managers. Large-MTU support is negotiated and makes F07 relevant. ServerCapabilities assembly in NegotiateProcessor.cs:49-103 does not advertise every feature for which code exists (notably leasing/persistent handles), while CREATE can still grant related contexts and a share can be marked continuously available. Capability bits, accepted create contexts, and backend guarantees should be audited as one matrix. Absence of optional DFS, quota, snapshot, sparse/reparse, RDMA, or other extensions is not by itself a protocol violation; returning an honest unsupported status is acceptable where the specification permits it. TLS/QUIC and all cryptographic negotiation details are outside this report.

Durable handles: ownership-related checks were excluded. In-memory retention and explicit timeout/scavenging paths exist. The persistence record is not a full open-state journal. This report does not certify crash recovery, failover, or continuous availability. F15 concerns visible missing reliability state, not authorization.

Coverage is targeted, not a line-by-line audit of all 328 files. There was no Windows/macOS/Linux client interoperability run, packet capture, stress test, filesystem fault injection, binary-level execution, formal cryptographic review, or complete RPC/Witness/DFS implementation audit. No runtime validation completed. The package/source files remain unchanged.

RECOMMENDED REPAIR ORDER

1. Prevent recursive directory deletion and repair open/close/rename lifecycle invariants.
2. Disable optional caching, multichannel and persistent/CA grants until their semantics are implemented and tested. Merely lowering the maximum dialect does not fix the basic filesystem and compound bugs.
3. Fix related compound execution and the credit ledger; implement complete request/response bounds and semantics.
4. Repair async registration/transmission ordering, lock cancellation, notification buffering and transactional failure cleanup.
5. Establish conformance checks and ordinary workload tests using the original binary or a clean maintained source build; then add cross-client, multichannel and recovery cases before re-enabling features.
